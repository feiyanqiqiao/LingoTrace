# LingoTrace 项目宪章

## 核心原则

### 一、用户价值优先，用户语言优先

用户面向 Agent 的学习任务必须支持自然语言表达；用户不需要记忆内部函数名、数据封套、命令参数或写入模式。新增能力必须说明用户价值、适用边界和失败时的可理解反馈。

### 二、核心能力与语言包职责分离

跨语言共享的上下文、能力开关、路径边界、写入保护和事务语义属于 LingoTrace core。字段、模板、路径角色、语言学规则、发音规则和语言特定的 Agent 指令属于对应语言包。只有至少两个语言包需要、能够抽象为语言无关行为且有一致测试契约的能力，才可以进入 core。

### 三、安全写入与人工内容保真不可妥协

任何可能改变现有学习状态的操作 MUST 先完成上下文、能力、路径和写入保护检查。覆盖、合并、移动或删除现有内容 MUST 先说明计划并获得所需确认；明确的复习结算可以遵循其内部预览与二次验证契约。系统 MUST 保留人工整理的正文、来源、复习提示和听力句子选择，不得以自动化整理为理由静默覆盖。

### 四、规格先行，变更可追溯

每项 substantive engineering work MUST 在实现前形成可审计的用户故事、验收标准、计划和任务；存在重大歧义时 MUST 先记录澄清决策。规格、计划、任务、实现和验证必须通过稳定的需求或用户故事标识互相追踪。实现与规格不一致时，必须更新规格或补充任务，不得静默接受漂移。

### 五、可执行证据优先

每项用户可见行为 MUST 有自动测试、架构基线或明确的人工评审证据。变更完成前 MUST 运行与风险相称的目标测试；跨平台、路径边界、隐私 allowlist 和语言包契约变更必须覆盖相应的集成或契约验证。通过测试不代表规格收敛，最终还必须核对实现、计划和任务是否完整一致。

### 六、公共运行时与私人 Vault 隔离

公共仓库只包含运行时、公开模板、工具、规格和测试；私人 Vault、学习笔记、音视频、转写产物、`.obsidian/` 状态、凭据和临时文件不得进入公共提交。所有公共变更 MUST 遵守 allowlist、分支、审查、CHANGELOG 和上游 PR 规则。

## 约束与安全边界

- 项目维护文档统一使用中文；代码、命令、路径、协议字段、测试名称和外部原文保留必要的原始形式。
- `.agents/skills/` 只接受当前 `specify` CLI 生成和验证的受管文件，不手工改写。
- 学习 Vault 与公共运行时分离；Vault 内的路径角色配置是真实来源，语言包路径文件只提供共享默认值。
- Agent Skill 不得直接写入 Vault；所有写入必须经过 core 和当前语言包能力。
- 普通学习者路径与开发者路径必须保持分离，不能要求学习者 fork、运行开发测试或阅读贡献流程。
- 现有能力契约和用户故事是当前行为参考；迁移到 Spec Kit 时保留其价值，不复制同一事实到多个互相竞争的规范位置。

## 工程流程与质量门禁

- 新的 substantive engineering work 按 `constitution → specify → clarify → plan → checklist → tasks → analyze → implement → validate → converge` 执行；`clarify`、`checklist` 和 `analyze` 可根据风险和歧义跳过，但必须说明理由。
- 实现前必须检查工作区、同步并比较 `main`、`origin/main` 和 `upstream/main`，从干净的 topic branch 开始，不直接开发或提交到 `main`。
- 代码、文档、模板或公共契约变更必须更新对应的中文当前文档；改变用户行为时，测试通过后、最终提交前更新 `CHANGELOG.md`。
- 提交前必须审查 staged 文件并运行 `bash tools/git/check-public-staged-files.sh`；不得提交私人 Vault 或受版权保护的学习材料。
- PR 必须说明用户可见变化、设计边界、测试结果、未验证事项和与适用规格的对应关系。所有必需 CI 通过后仍需等待维护者审查和合并。

## 治理

本宪章是项目工程决策的稳定约束。用户明确指令、更高优先级的运行时安全规则和平台限制优先于本宪章；在项目范围内，规格、计划、任务和实现必须服从本宪章。原则变更必须通过 Spec Kit Constitution 流程，写明影响报告、版本变更、迁移影响和验证证据。版本遵循语义化版本：新增或实质扩展原则提升 MINOR，破坏既有治理约束提升 MAJOR，纯澄清提升 PATCH。每次 PR 都必须检查适用原则；若发现违规，必须在合并前修复或在 PR 中记录经维护者接受的例外及后续任务。
